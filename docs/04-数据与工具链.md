# 04 · 数据与工具链：RPC、数据源、监控技术与成本

> 目的：为"只读预警 + 筛选"系统准备可落地的技术选型。
> 更新日期：2026-10-03。**所有额度、价格、接口方法以服务商官方文档为准，落地前核验。**

## 1. 总体思路：执行外包，监控自研

| 能力 | 建议做法 | 理由 |
|:-----|:---------|:-----|
| 下单/卖出 | 用现成交易终端 | 自研速度拼不过专业队，工程成本却极高 |
| 新币预警 | **自研（本项目）** | 这是唯一能建立信息和筛选优势的地方 |
| 链上筛选 | 自研 + 第三方风险 API | 组合使用，降低误判 |
| 行情/风控数据 | 第三方数据源 | 自建成本过高 |

结论：本项目自研范围锁定在**采集 → 筛选 → 告警 → 记录**，不碰下单。

## 2. RPC 层

### 2.1 选择

- **公共 RPC**：免费但限流严重、稳定性差，只适合学习。
- **托管 RPC（Helius / QuickNode / Triton 等）**：有免费档，付费档提供更强的 websocket 与历史查询能力。
- **自建节点**：成本高、运维重，本项目不需要。

建议：先用托管 RPC 免费档跑通，确认真实用量后再考虑付费档。

### 2.2 需要的调用能力

- `logsSubscribe`：监听目标程序的日志，用于捕获新池/新代币事件。
- `accountSubscribe` / `programSubscribe`：监听账户或程序状态变化。
- `getAccountInfo` / `getTokenSupply`：读取 mint 权限、供应量等基础信息。
- `getTokenLargestAccounts`：读取持币集中度。
- `getSignaturesForAddress`：追踪特定地址（dev / 聪明钱）的近期行为。

> 具体方法签名与限制以 Solana 官方 RPC 文档为准，不同服务商支持程度不同。

## 3. 数据源

| 数据 | 用途 | 候选来源 | 备注 |
|:-----|:-----|:---------|:-----|
| 价格/流动性/成交 | 行情与筛选 | DexScreener、Birdeye 等 | 注意免费额度与条款 |
| 风险检测 | 蜜罐/rug 初筛 | Rugcheck 类工具 | 只能作为参考，不能替代试卖 |
| 持币关系图 | 识别绑定地址 | Bubblemaps 类工具 | 图形化，人工复核为主 |
| 链上明细 | 权限、供应、交易 | 区块浏览器 / RPC | 最权威的一手数据 |
| 社交热度 | 叙事判断 | X、Telegram | 反女巫难度大，人工为主 |

**许可提醒**：使用第三方 API 前确认 ToS 与再分发限制，避免把受限数据用于对外产品。

## 4. 监控技术要点

1. **事件驱动优先**：用 websocket 订阅而非轮询，降低延迟和配额消耗。
2. **去重与幂等**：同一代币可能触发多次事件，需按 mint 地址去重。
3. **背压处理**：新币爆发时事件量会瞬间冲高，采集层要有队列和丢弃策略。
4. **限流与重连**：所有外部调用要有超时、指数退避重试和断线重连。
5. **时间戳统一**：所有事件记录 UTC 时间戳，便于后续复盘对齐。

## 8. 实测结论（2026-10-03）

以下是本机上真实跑通后记录的事实，不是推测。

**8.1 代理环境下的 WebSocket**

本机走本地代理（例如 `http_proxy=127.0.0.1:7890`）。Node 的 `fetch` 默认不读代理环境变量，
而 `@solana/web3.js` 的订阅走 `rpc-websockets`，也没有暴露 `agent` 参数。表现是：
HTTP 请求正常、`logsSubscribe` 静默超时（`ws error: connect ETIMEDOUT`）。

解决方案（已在 `src/proxy.ts` 实现）：

1. 启动脚本设置 `NODE_USE_ENV_PROXY=1`，让 `fetch` 走代理。
2. 启动时把 `rpc-websockets` 的 `WebSocket` 工厂包一层，注入 `https-proxy-agent` /
   `socks-proxy-agent`，让 wss 也能走代理。无代理环境下自动跳过。

**8.2 交易版本**

主网已出现 v1 交易。`maxSupportedTransactionVersion: 0` 会导致
`Transaction version (1) is not supported`，必须设为 `1`（见 `config/default.yaml`）。

**8.3 程序日志不等于发币事件**

订阅程序日志会收到该程序的**每一笔**交易。实测 25 秒内 pump.fun 产生约 4.8 万条日志行，
其中绝大多数是买卖、ATA 创建和失败交易，真正的发币只占极小比例。这是队列打满和
RPC 限流的根因。

**8.4 日志预过滤是必需的**

用 `scripts/watch-logs.ts` 采样 + `scripts/probe-creation.ts` 实测精度，得到：

| 特征串 | 实测精度 | 结论 |
|:-------|:---------|:-----|
| `Program log: Create` | 0% | ❌ 不是发币标记 |
| `Instruction: Create` | 约 50% | ✅ 采用为默认过滤串 |

50% 精度意味着约一半回查是无效的，但把无关交易削减了 99% 以上，性价比很高。

**8.5 公共 RPC 不足以支撑**

公共主网 RPC 在这种负载下频繁返回 429，即使加了过滤也会持续退避重试。
**要持续运行必须使用专用 RPC**（Helius / QuickNode / Triton 等）。
公共 RPC 只适合用 `scripts/fetch-once.ts` 做单笔验证。

**8.6 持币数会被静默降级为 0（已修）**

对已落库的 134 个 pump.fun 候选做复盘发现：`holder_count` **全部为 0**，
且 `enrich_errors` 里没有对应的报错。但同一批 mint 的 `supply` 是 1e15 / 2e15
（正供给），而正供给的 SPL 代币必然至少存在于一个 token 账户中——
也就是说这个 0 不是真实值，是公共 RPC 对 `getProgramAccounts` 静默返回了空集。

危害：空集被当成"持币地址 0 < 50"命中硬性否决，导致**所有新币被误杀**，
筛选层永远无法产出 pass/manual。

修复（`src/enricher.ts`）：只有"供给确认为 0"时，0 账户才可信；
否则 0 账户判为 `unknown`（`holderCount = null` 并记录 `enrich_errors`），
由筛选层按配置的 `unknown: manual` 走人工复核。新增 6 项单元测试覆盖该不变量。

**后续（已实现）**：修复后仍有问题——新发行代币的 `liquidity_usd` 为 `null`
（DexScreener 尚无交易对），会命中 `minLiquidityUsd: unknown: reject`；
`minHolderCount: 50` 对新币也几乎必然不达标，导致"新币全部 reject"。

处理方式：不擅自改阈值，而是引入 **`screening.freshGraceSec`**（默认 900s）。
宽限期内，`min_liquidity` / `max_top10` / `min_holders` 这三条"质量/活跃度"
规则未达标时降级为 `manual`（记录 + 人工复核），安全类规则（mint/freeze 权限、
税率、LP）不受影响，仍会硬性否决。阈值本身保持原值，等积累真实数据后回归调整。

**8.7 M3 回填（已实现）**

新增 `market_snapshots` 表与 `scripts/backfill.ts`：定期对已跟踪代币重新抓取
DexScreener 市场数据并落成时序快照；`npm run backfill:report` 离线输出
首→末涨跌统计（胜/负/近归零 -99%、均值、中位数、最好/最差）。
长跑进程每 10 分钟自动快照一次。这样一个月后可以用真实数据回答"pass 的币
后来涨了还是归零了"，而不只是靠感觉。
