# 06 · 技术方案：只读预警 + 筛选系统

> 目的：定义第一阶段要落地的工具——**只读、不下单**的预警与筛选系统。
> 更新日期：2026-10-03。状态：M0–M3 已实现，待联网连续运行验证。

## 1. 目标与非目标

**目标**

1. 第一时间发现 Solana 上的新池/新代币。
2. 自动跑一遍 `docs/03` 的过滤与评分，推送到 Telegram。
3. 把每个候选落库，供后续复盘。

**非目标**

- 不签名、不下单、不持有私钥、不接触资金。
- 不做自动卖出，"执行"仍由人手动在终端完成。

这样设计的原因：执行层自研的工程/基建成本远高于娱乐收益，而预警层是唯一能建立筛选优势的地方。

## 2. 架构

```
        ┌──────────────┐
        │  采集层       │  websocket 订阅新池/新代币事件
        │  Collector   │  (logsSubscribe / programSubscribe)
        └──────┬───────┘
               │ raw events (queue, dedupe by mint)
        ┌──────▼───────┐
        │  标准层       │  补齐链上字段：权限、供应、持仓、LP
        │  Enricher    │
        └──────┬───────┘
               │ normalized token record
        ┌──────▼───────┐
        │  过滤/评分层  │  硬性否决清单 → 评分卡 → verdict
        │  Screener    │
        └──────┬───────┘
               │ pass / reject / manual
        ┌──────▼───────┐        ┌──────────────┐
        │  告警层       │───────▶│  Telegram    │
        │  Notifier    │        └──────────────┘
        └──────┬───────┘
               │
        ┌──────▼───────┐
        │  记录层       │  SQLite / CSV 落盘
        │  Store       │
        └──────────────┘
```

## 3. 组件设计

### 3.1 采集层 Collector

- 通过 websocket 订阅目标程序日志，捕获新池/新代币创建事件。
- 事件进入内存队列，按 `mint` 地址去重。
- 处理背压：队列超限时按时间窗口丢弃低优先事件并计数告警。
- 断线自动重连（指数退避），重连后补齐时间窗口。

### 3.2 标准层 Enricher

对每个候选代币补齐字段：

- mint / freeze authority 状态
- 总供应量、是否可变
- LP 地址、流动性规模、锁定状态
- 持币地址数、前 10 占比
- 买卖税、交易活跃度

外部调用统一封装：超时、重试、限流、结果缓存。

### 3.3 过滤/评分层 Screener

两段式：

1. **硬性否决**（对应 `docs/03` 第 6 节）：任一条命中 → `reject`，直接结束。
2. **评分卡**：对通过的标的加权打分 → `pass`（达阈值）/ `manual`（接近阈值，人工复核）。

评分权重与阈值做成**配置项**，不写死在代码里，方便用真实数据回归调整。

### 3.4 告警层 Notifier

- 通过 Telegram Bot 推送。消息字段：

```
🟡 新候选 [pass]
代币: <symbol> (<mint 短地址>)
市值: $xxx | 流动性: $xxx
持币数: xxx | Top10: xx% | 税: x%
权限: mint 放弃 / freeze 放弃 | LP: 已锁
评分: 78 / 100
链接: dexscreener / 浏览器
```

- 分级：`pass` 立即推送，`manual` 汇总推送或静默入表。
- 去重：同一代币只推一次；状态变化（如流动性骤降）可追加告警。

### 3.5 记录层 Store

- SQLite 落盘，字段见 `docs/04` 第 5 节。
- 每条记录含：观测时间、来源、各维度原始值、评分、结论、后续表现。
- 用于回填"事后验证"：这个 pass 的币后来涨了还是归零了。
- M3 回填：另有 `market_snapshots` 表，按 `(mint, observed_at)` 记录价格/市值/
  流动性时序；`scripts/backfill.ts` 定期快照并可输出首→末涨跌统计。

## 4. 技术选型（建议）

| 层 | 建议 | 说明 |
|:---|:-----|:-----|
| 语言 | Python 或 TypeScript | 生态成熟，迭代快 |
| websocket | 官方 SDK / `websockets` | 稳定重连 |
| 存储 | SQLite | 单机足够，零运维 |
| 推送 | Telegram Bot API | 免费、简单 |
| 配置 | YAML/JSON | 权重阈值可调 |
| 运行 | 本机 or 云主机 | 初期本机 |

## 5. 里程碑

| 里程碑 | 内容 | 验收标准 |
|:-------|:-----|:---------|
| M0 | 采集层跑通 | 能稳定收到新池事件并落库，去重有效 |
| M1 | 标准层补齐 | 每个代币能拿到权限/流动性/持币字段 |
| M2 | 筛选 + 推送 | 达到阈值的代币能推送到 Telegram |
| M3 | 回填验证 | 能对历史候选自动回填涨跌，输出统计 |

状态（2026-10-03）：M0–M2 已完成；M3 代码已完成（`src/backfill.ts` +
`scripts/backfill.ts`，含单元测试），实际统计需联网累积快照后才有数据。

## 6. 安全要求

- 全系统**只读**，不包含任何私钥或签名逻辑。
- API Key 走环境变量，不入库、不入日志。
- 推送内容不含任何敏感信息。
- 所有真实资金操作由人手动完成。

## 7. 已决策项

- [x] 语言：TypeScript（Node 22）。理由：官方 `@solana/web3.js` 最完整，
      事件驱动模型契合采集+推送，开发速度优先（瓶颈在数据源不在语言）。
- [x] 存储：SQLite（Node 内置 `node:sqlite`，零原生依赖）。
- [x] 推送：Telegram，未配置时自动降级为 stdout。
- [x] 评分卡：初始权重与阈值见 `config/default.yaml`，全部可配置，
      跑一个月后用真实数据回归调整。
- [x] 数据源：链上 RPC + DexScreener（市场数据），不依赖交易所钱包接口。
- [ ] RPC 服务商：待定。公共 RPC 实测会 429，持续运行需专用 RPC（见 `docs/04` 第 8.5 节）。

已知问题（2026-10-03 复盘）：公共 RPC 会把 `getProgramAccounts` 静默降级为空集，
导致持币数被记成 0 并误杀全部候选。已在 `src/enricher.ts` 修复为按供给量不变量
判为 `unknown`，详见 `docs/04` 8.6。新币的流动性/持币/分布数据在发现时天然缺失，
因此引入 `screening.freshGraceSec`：宽限期内这三个"质量"维度未达标降级为
`manual`（人工复核），安全类规则不受影响。阈值本身保持原值，等真实数据回归。

## 9. 运行 M3 回填

```bash
npm run backfill           # 对已跟踪代币快照一次市场数据（需联网）
npm run backfill:report    # 离线输出首→末涨跌统计（胜/负/近归零、均值、中位数）
```

长跑进程（`npm start`）每 10 分钟自动执行一次快照；`minIntervalSec`、`maxAgeHours`
等参数见 `src/backfill.ts` 的 `DEFAULT_BACKFILL_OPTIONS`。
